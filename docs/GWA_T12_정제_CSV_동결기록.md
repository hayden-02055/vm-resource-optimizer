## 2. 동결된 데이터 형상

- **행 수:** 11,221,800 (동결본과 일치, 행 순서도 동일)
- **컬럼:** 12개. 이름·순서·dtype은 로딩 동결기록 §2와 같다 — `vm_id`(`int64`), `Timestamp [ms]`·`CPU cores`(`Int64`), 나머지 9개(`float64`)
- **인코딩:** UTF-8, BOM 없음(선두 `76 6d 5f`) / 줄바꿈 LF(CR 0개) / 구분자 `,` / 모든 행의 필드 수 12 / 빈 필드 0개 / `.tmp` 잔여물 없음
- **읽기 방법:** `pd.read_csv(path, dtype={'Timestamp [ms]': 'Int64', 'CPU cores': 'Int64'})`. 값 대조가 필요하면 `float_precision="round_trip"`을 추가한다(스크립트의 검증 방식).

## 4. 재현 및 무결성 대조 절차

```bash
# (a) 정제본과 생성 코드가 동결 시점과 같은지 확인
shasum -a 256 data/vm_all_1250_clean.csv src/build_clean_csv.py tests/test_build_clean_csv.py

# (b) 정제본과 동결본의 관계 — set_nan 이벤트가 0건인 동안은 같아야 한다
cmp data/vm_all_1250_loaded.csv data/vm_all_1250_clean.csv

# (c) 입력·의존 기준선
shasum -a 256 data/vm_all_1250_loaded.csv data/quality/anomaly_events.csv \
              src/clean_data.py tests/conftest.py

# (d) 다시 생성 (출력은 동일 체크섬이어야 한다)
python3 src/build_clean_csv.py
python3 -m pytest tests -q
```

(a)가 달라졌다면 정제본이나 생성 코드가 바뀐 것이다. (c)가 달라졌다면 입력이나 판정 결과가 바뀐 것이므로 정제본을 다시 만들고 새 동결 항목을 추가해야 한다.

## 5. 동결 시점에 관측된 사실 (해석·처리는 미정)

1. **정제 단계의 결과는 "값 변경 없음 + 품질 로그"다.** 정제본은 동결본과 바이트 단위로 같고, 이상치·판정 정보는 `data/quality/`의 로그에만 있다. 후속 단계에서 이 정보를 쓰려면 로그를 `(vm_id, timestamp_raw, metric)` 키로 정제본에 붙여야 한다.
2. **정제본에는 아래 항목이 원본 그대로 남아 있다.** 모두 학습 데이터 구성 단계의 안건이다.
   - 중복 시각 행: 인접 간격 0인 행 452,577개(VM 122개, 슬라이스 A 동결기록 §5-4)
   - 할당 0 행: `CPU cores = 0` 1,593,544행(구간 224개, 모두 VM 선두·후미)
   - `CPU usage [%]` 컬럼(사실상 중복, 제거 미정)
   - `Timestamp [ms]` 컬럼명(실제 단위는 초로 보임, 개명 미정)
3. **결측 셀이 0개다.** 지금 기준으로는 결측 보간 단계에서 처리할 대상이 없다.

## 6. 동결 이후 변경 규칙

- `data/vm_all_1250_clean.csv`는 후속 단계의 **입력으로만 읽는다.** 덮어쓰지 않는다.
- 컬럼 제거·개명, 중복 행 정리, 할당 0 구간 제외 같은 가공은 정제본을 바꾸지 않고 **별도 파일**로 만든다.
- 판정 규칙(임계값 등)이 바뀌어 판정 로그가 다시 만들어지면, `src/build_clean_csv.py`를 다시 실행하고 이 문서를 지우지 않은 채 **새 동결 항목을 추가**한다. `set_nan` 이벤트가 생기면 §4(b)의 `cmp` 관계는 더 이상 성립하지 않는 것이 정상이다.
- `data/vm_all_1250_loaded.csv`와 `data/quality/` 로그는 계속 읽기 전용이다(로딩 동결기록 §6, 슬라이스 B 동결기록 §6).

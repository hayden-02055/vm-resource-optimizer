# GWA-T-12 데이터 로딩 최종 설계안 (rev.2)

> **프로젝트:** 머신러닝 기반 가상머신 자원 사용량 예측 및 동적 자원 할당 시스템
> **대상 데이터:** GWA-T-12 BitBrains — `fastStorage` (압축 해제 상태로 저장소에 포함)
> **사용 도구:** `pandas`, `numpy` + Python 표준 라이브러리 (`pathlib`, `re`, `argparse`)
> **범위:** 데이터 **로딩과 스키마 구성**만 다룸. 이상치·결측값 보정·모델 학습은 이번 단계에서 결정하지 않음.
> **상태:** rev.2 기준 **로딩 완료 및 검수 통과**. 구현체는 `src/load_data.py`.

## 1. 결론: 로딩 원칙

1. **원본 디렉터리는 수정하지 않는다.** `data/fastStorage/2013-8/` 아래 VM별 CSV 1,250개를 읽기 전용으로 순회한다.
2. `pandas.read_csv(..., chunksize=100_000)`을 사용해 **청크 단위**로 읽고 저장한다. 전체 행을 한 번에 메모리로 올리지 않는다.
3. **원본 11개 컬럼은 로딩 단계에서 모두 보존**한다. `CPU cores`는 VM별로 다르므로 반드시 유지한다.
4. `Timestamp [ms]`는 **원본 숫자·행 순서를 그대로 유지**한다. 날짜 변환·상대시간화·보간·정렬은 로딩 단계에서 하지 않는다.
5. 서로 다른 VM의 시계열을 혼동하지 않도록 **`vm_id`를 추가**한다. 원본 경로와 행 수는 별도 **manifest**로 기록한다.
6. 산출물은 **단일 병합 CSV** 한 개다 (§3 결정 기록 참조).
7. CPU/Memory와 Disk/Network는 **두 그룹으로 논리적으로 분류**하지만, **컬럼이나 행을 분리하지는 않는다**. 같은 시점의 상호 관계를 나중에 분석하기 위함이다.
8. `CPU usage [%]`는 다른 컬럼으로 계산되는 중복 후보이므로 **정제 단계에서 제거 여부를 확정**한다. 로딩 단계에서는 버리지 않는다.
9. 값 변환에 실패하거나 결측이 생기면 **조용히 넘기지 않고 오류를 발생**시킨다. 데이터 보정 규칙을 로딩 단계에서 임의 적용하지 않기 위함이다.

### 공식 출처와 전체 원본에서 확인한 사실

- [GWA-T-12 공식 데이터 설명](https://atlarge-research.com/gwa-t-12/)에 따르면 총 **1,750개 VM**이며, `fastStorage` **1,250개**, `Rnd` **500개**로 구분된다. 각 파일에는 한 VM의 측정값이 기록되어 있다.
- 공식 설명은 컬럼 구분자를 **세미콜론 + 탭(`;\t`)**으로 안내한다. **전체 1,250개 파일을 확인한 결과 헤더와 데이터 행이 모두 `;\t`로 동일하다.** (rev.1의 "헤더 탭 2개 / 데이터 탭 1개" 서술은 오류였으므로 폐기)
- 데이터 행의 세미콜론은 필드당 1개씩 **총 10개**이며(마지막 필드 뒤에는 없음), `;`로 분리하면 **11개 필드**가 된다. 각 필드 앞에 탭이 남지만 pandas 수치 변환이 선행 공백을 허용한다.
- **1,250개 파일의 헤더가 모두 동일**하다(`sort -u` 결과 1종). 비수치 토큰 **0개**, 빈 필드 **0개**.
- `Timestamp [ms]`라는 컬럼명과 달리 샘플 값 `1376314846`은 **초 단위 Unix 시간처럼 보인다**(연속 3행 간격 300). 단위가 모호하므로 **로딩 중 값을 바꾸지 않고**, 정제 단계에서 단위를 문서화한다.
- `Rnd` 트레이스는 아직 저장소에 없다. 구분자 자동 판별은 `Rnd` 합류 시를 대비한 요구사항으로 유지한다.

## 2. 스키마: 무엇을 읽고 남길 것인가

| # | 논리 그룹 | 컬럼 | dtype | 로딩 단계 | 향후 검토 |
|---|---|---|---|---|---|
| 1 | 식별 정보(추가) | `vm_id` | `int64` | **추가** | 원본 파일명(1~1250) |
| 2 | 공통 시간 | `Timestamp [ms]` | `Int64` | 원본 값 그대로 유지 | 단위 확인만 별도 수행 |
| 3 | CPU/Memory | `CPU cores` | `Int64` | **유지** | VM별 코어 수가 다름 |
| 4 | CPU/Memory | `CPU capacity provisioned [MHZ]` | `float64` | 유지 | 동적 할당 판단에 필요 |
| 5 | CPU/Memory | `CPU usage [MHZ]` | `float64` | 유지 | CPU 절대 사용량 |
| 6 | CPU/Memory | `CPU usage [%]` | `float64` | **일단 유지** | 전체 검증 후 중복 시 제거 |
| 7 | CPU/Memory | `Memory capacity provisioned [KB]` | `float64` | 유지 | 할당 메모리 용량 |
| 8 | CPU/Memory | `Memory usage [KB]` | `float64` | 유지 | 메모리 사용량 |
| 9 | Disk/Network | `Disk read throughput [KB/s]` | `float64` | 유지 | 읽기 방향 처리량 |
| 10 | Disk/Network | `Disk write throughput [KB/s]` | `float64` | 유지 | 쓰기 방향 처리량 |
| 11 | Disk/Network | `Network received throughput [KB/s]` | `float64` | 유지 | 수신 방향 처리량 |
| 12 | Disk/Network | `Network transmitted throughput [KB/s]` | `float64` | 유지 | 송신 방향 처리량 |

**로딩 직후:** 원본 11개 + `vm_id` 1개 = **12개 컬럼 × 11,221,800행**.
**후속 정제에서 `CPU usage [%]` 제거 시:** 10개 원본 + `vm_id` = **11개 컬럼**.

컬럼명은 **원본 표기(공백·대괄호·단위 포함)를 그대로 유지**한다. 단위 추적이 가능하도록 하기 위함이며, `snake_case` 개명은 정제 단계에서 결정한다.

> 읽을 때 `dtype={'Timestamp [ms]': 'Int64', 'CPU cores': 'Int64'}`를 지정한다. 지정하지 않으면 pandas가 `int64`로 추론하지만, 결측이 생긴 뒤에는 `float64`로 흔들리므로 명시한다.

> `trace_type`은 현재 `fastStorage`만 사용하므로 모든 행에 반복 저장하지 않고 manifest에 기록한다. 추후 `Rnd`까지 합쳐 **단일 학습 테이블**로 만들면 `trace_type` 컬럼을 추가하거나 복합 키 `(trace_type, vm_id, timestamp)`를 사용한다.

### 결정 기록: 단일 병합 CSV 채택

| | 단일 병합 CSV **(채택)** | VM별 CSV 1,250개 (기각) |
|---|---|---|
| 적합한 학습 방식 | 전체 VM 통합 모델 | VM별 개별 모델 |
| 로드 | 한 번에 읽거나 `chunksize`로 순회 | 1,250개 파일 관리 필요 |
| 파일 수 | 2개(데이터+manifest) | 1,251개 |

**채택 근거:** 본 프로젝트는 VM 전체를 아우르는 통합 예측 모델을 목표로 하므로, 학습 시 매번 1,250개 파일을 재조립할 이유가 없다. `vm_id` 컬럼과 manifest가 있으므로 단일 파일에서도 VM 단위 분리가 언제든 가능하다.
**기각 근거:** VM별 파일은 VM 단위 병렬 실험에 유리하지만, 그 이점은 `groupby('vm_id')`로 대체할 수 있고 파일 관리 비용이 더 크다.

rev.1의 "`pd.concat()`으로 합치지 않는다 / VM별 CSV로 저장한다"는 조항은 이 결정으로 **폐기**한다. 단, **메모리에서 전체를 `concat`하지 않는다**는 제약은 유지한다 — 청크를 즉시 디스크에 이어 쓴다.

## 4. 로딩 절차

1. **파일 목록 수집:** `data/fastStorage/2013-8/`을 순회해 데이터 파일을 번호순(1~1250)으로 정렬한다. 대상에서 제외한 파일은 개수와 이름을 기록한다.
2. **구분자 판별:** 각 파일의 첫 데이터 행을 보고 `;` / `\t` 중 올바른 구분자를 결정한다. 한 트레이스 안에서도 파일별로 독립 판별한다.
3. **헤더 검사:** 공식 11개 컬럼과 이름·순서가 같은지 확인한다. 다르면 기대값과 실제값을 함께 띄우고 **오류로 중단**한다.
4. **자료형 지정:** `Timestamp [ms]`, `CPU cores`는 nullable 정수(`Int64`); 나머지 수치는 `float64`로 읽는다.
5. **청크 순회:** `chunksize=100_000`으로 읽고 `vm_id`만 추가한다. 값은 변환하지 않는다.
6. **결측 검사:** 청크에서 NaN이 발견되면 컬럼별 건수와 함께 **오류로 중단**한다. (§1-9)
7. **행 수 대조:** 파일별로 `원본 데이터 행 수 == 적재 행 수`를 확인하고, 마지막에 전체 합계를 한 번 더 대조한다.
8. **단일 CSV 적재:** 임시 파일(`*.tmp`)에 이어 쓴 뒤 완료 시 원자적으로 교체한다. 인코딩은 `utf-8`(BOM 없음).
9. **manifest 작성:** 파일별 `trace` · 원본 경로 · `vm_id` · 행 수 · 구분자 · 출력 경로를 남긴다.

### 구현체: `src/load_data.py`

실행 코드는 **설계안에 복사해 두지 않는다.** 문서와 코드가 어긋나는 것을 막기 위해, 구현의 유일한 권위는 `src/load_data.py`로 두고 설계안은 위 계약만 규정한다.

```bash
# 기본 경로로 실행
python3 src/load_data.py

# 경로를 바꿀 때 (Rnd 등)
python3 src/load_data.py \
  --input-dir data/Rnd/<하위폴더> \
  --output data/rnd_all_loaded.csv \
  --manifest data/Rnd_loading_manifest.csv
```

하드코딩 경로를 두지 않는다. 기본값은 저장소 루트 기준 상대 경로로 해석한다.

> **메모 1:** `6.7108864E7` 같은 지수 표기는 출력 시 `67108864.0`으로 평문화된다. float64 왕복이므로 **값과 정밀도는 동일**하다.
> **메모 2:** rev.1에 있던 ZIP(`zipfile`) 순회 절차는 저장소에 ZIP이 없으므로 **폐기**한다. 디렉터리 순회로 대체했다. ZIP 재배포본을 다시 다룰 필요가 생기면 압축 해제 후 본 절차를 적용한다.

## 6. 다음 회의에 넘길 판단 항목

로딩 과정에서 관측된 사실만 적는다. **해석과 처리 정책은 정하지 않았다.**

1. **`CPU cores = 0`인 행이 존재한다.** 전체 고유값: `0, 1, 2, 4, 6, 8, 16, 32`. 코어 0은 물리적으로 성립하지 않으므로 이상치 정책 대상이다.
2. **VM별 행 수 편차가 극심하다.** 최소 **5행**(vm 312) ~ 최대 **23,692행**(vm 842).

   | 행 수 구간 | VM 개수 |
   |---|---|
   | 10행 미만 | 3 |
   | 10 ~ 99 | 6 |
   | 100 ~ 999 | 7 |
   | 1,000 ~ 7,999 | 80 |
   | 8,000 이상 | 1,154 |

   시계열 학습에 투입할 **최소 관측 길이 기준**이 필요하다.
3. **`CPU usage [%]` 제거 여부:** `CPU usage [MHZ] / CPU capacity provisioned [MHZ] × 100`과의 일치 여부를 전체 데이터에서 확인한 후 결정한다.
4. **Timestamp 해석:** 값 범위와 기록 간격을 확인해 단위(초 vs 밀리초)를 문서로 명시하되, 원본은 유지한다.
5. **이상치 정책:** 로딩이 완료되었으므로 별도 회의에서 논의한다. (`docs/GWA_T12_이상치_정제_전략.md` 참조)
6. **`Rnd` 트레이스 합류 여부:** 합류 시 `trace_type` 컬럼 또는 복합 키 도입이 필요하다 (§2 메모).
